# Safety contract — repoops v1

## Core rule

`repoops` is a metadata reporter. It is not a repository repair tool.

## Forbidden Git commands

The implementation must not run:

```text
git pull
git push
git reset
git clean
git checkout
git switch
git add
git commit
git stash
```

## Allowed Git commands

The implementation may run only:

```text
git rev-parse --is-inside-work-tree
git rev-parse --abbrev-ref HEAD
git rev-parse --short HEAD
git status --porcelain=v1
git rev-parse --abbrev-ref --symbolic-full-name @{u}
git rev-list --count @{u}..HEAD
git rev-list --count HEAD..@{u}
```

All of the above are read-only and metadata-only — they inspect local refs and never touch the network or the working tree.

### Additional commands for `repoops checkpoint` / `repoops resume`

`repoops.handoff` (backing `repoops checkpoint`/`repoops resume`) adds five more
commands to the same `ALLOWED_GIT_COMMANDS` whitelist in `git_scan.py`, enforced by
the same `_run_git`:

```text
git rev-parse --show-toplevel
git rev-parse HEAD
git diff --stat
git diff --cached --stat
git log -5 --pretty=format:%h<US>%ad<US>%s --date=iso-strict
```

All five are read-only and never touch the network. `diff --stat`/`diff --cached
--stat` report changed filenames and insertion/deletion counts only — never file
contents or the actual diff body — which satisfies "never include full diffs"
below. `log` is capped at a fixed 5-commit limit, not configurable. `repoops
checkpoint`/`repoops resume` never call `git fetch`: ahead/behind are always
computed from local refs only, the same way as `repoops scan` without `--fetch`.

## Command whitelist enforcement

The Git commands above are enforced in code, not just by convention: `src/repoops/git_scan.py` holds an `ALLOWED_GIT_COMMANDS` set of exact argument tuples, and the internal `_run_git` helper raises `ValueError` if asked to run anything outside it. This is defense-in-depth — even a future bug that tried to run an unlisted command would be rejected before `subprocess` ever executes it. Any change to a git invocation (new flags, new order) requires a matching whitelist update; this is an intentional maintenance cost for a safety-critical tool.

## Fetch (opt-in, metadata only)

```text
git fetch --prune
```

`git fetch --prune` is the **only** network-touching command in `repoops`, and it is treated differently from the read-only commands above:

- **Opt-in only.** It runs only when `defaults.fetch: true` in config, or `--fetch` is passed on the CLI (see `docs/CLI_CONTRACT.md`). The default is `fetch: false` — no network access unless explicitly requested.
- **Separately whitelisted.** It is validated against its own `ALLOWED_FETCH_COMMANDS` set and run through a dedicated `_run_fetch` helper, never through `_run_git`. This means broadening the read-only whitelist can never accidentally permit fetch.
- **Updates remote-tracking refs only** (e.g. `origin/main`). It never modifies the working tree, never merges, and is never `git pull`.
- **Bounded by `defaults.fetch_timeout_seconds`** (`subprocess` timeout) and runs with `GIT_TERMINAL_PROMPT=0` so a misconfigured remote can never hang on an interactive credential prompt in a headless cron context.
- **Non-fatal on failure.** A failed or timed-out fetch is recorded as a sanitized `fetch_error` on that repo's snapshot (and the `fetch_failed` risk flag), never raised as an exception that would abort the rest of the scan.

## Secret handling

The scanner may see changed file paths from Git status. It must not read file contents.

Secret-like path indicators include:

```text
.env
secret
secrets
credential
credentials
token
key
private
pem
id_rsa
id_ed25519
```

If a changed path is secret-like:

1. count it normally;
2. add `possible_secret_file`;
3. redact it before rendering or notifying.

## Redaction examples

```text
.env -> [REDACTED_SECRET_PATH]
config/prod.credentials.json -> config/[REDACTED_SECRET_PATH]
secrets/api_token.txt -> [REDACTED_SECRET_PATH]/[REDACTED_SECRET_PATH]
```

## Fetch error sanitization

`git fetch` stderr can, in exotic remote configurations, contain a credential-embedded URL (e.g. `https://user:token@host/repo.git`). Raw stderr is never stored or rendered. Before becoming `fetch_error`, it is reduced by a pure `_sanitize_git_error` function: only the first line is kept, any `scheme://...` substring is replaced wholesale with `[REDACTED_URL]`, and the result is capped to 200 characters. This holds by construction, not because test fixtures happen to use local paths.

## Notification rule

Notification backends must receive only the Markdown report generated by `repoops.report`, never raw Git output, full diffs, environment values, or file contents.

## Telegram backend

`repoops.telegram` is a pure HTTP transport (stdlib `urllib` only) that knows nothing about config, snapshots, or reports — it only sends a bot token, chat ID, and text string. `repoops.notify` is the only caller and is responsible for:

- resolving `REPOOPS_TELEGRAM_BOT_TOKEN` / `REPOOPS_TELEGRAM_CHAT_ID` from the environment, never from YAML config, and never logging their values;
- condensing the rendered Markdown report to a short synthesis (header, Summary, Attention summary — everything before the per-repo `## Repositories` section) before sending, so phone notifications stay small and never include per-repo detail lines;
- capping the message to Telegram's 4096-character limit.

Failures are sanitized before becoming an error message or a `NotifyResult.reason`: `repoops.telegram` builds error text only from the HTTP status code or the low-level connection reason, never from the request URL, which embeds the bot token. A failed send is non-fatal — like `fetch_failed`, it is reported as `skipped` rather than raised, so a bad token or unreachable network never aborts `repoops run`. Missing environment variables are the one exception: those raise, since that is a configuration error the operator must fix before notifications can work at all — the error names the missing variable, never its value.

## Handoff checkpoints (`repoops.handoff`)

`repoops checkpoint`/`repoops resume` are subject to the same core rule: read-only
metadata inspection, with one narrow, explicit exception.

- **The only repository mutation `repoops` performs anywhere.** `repoops checkpoint`
  writes exactly two files: `.repoops/handoff.json` and `.repoops/HANDOFF.md`, both
  via an atomic same-directory temp-file-plus-rename (`repoops.paths.atomic_write_text`)
  so a crash mid-write never leaves a partially-written handoff. `repoops resume`
  never writes anything — it only reads `.repoops/handoff.json` and prints a report.
- **Never runs a mutating Git command.** Same forbidden list as the core rule above:
  no `pull`, `push`, `reset`, `clean`, `checkout`, `switch`, `add`, `commit`, `stash`.
  `repoops checkpoint`/`resume` create/read plain files under `.repoops/` directly
  with Python's filesystem APIs — they never ask Git to touch the index or working
  tree.
- **Never fetches.** Ahead/behind/upstream reuse `git_scan._remote_sync_status` with
  `fetch` hard-coded to `False` — `repoops checkpoint`/`resume` have no `--fetch`
  flag and no config option to enable one.
- **Never reads file contents or full diffs.** Only `git diff --stat`/`git diff
  --cached --stat` (filenames + line-change counts) are used — see "Allowed Git
  commands" above.
- **No LLM is ever invoked internally.** The `semantic` and `next_action` sections
  of a checkpoint are always written as literal `TODO:` placeholders — never
  generated, inferred, or asserted as fact — for a human or an external coding
  agent to fill in after the file is written.
- **Redacts secret-like paths in three places, not just one.** `notable_paths`
  reuses `git_scan.redact_secret_like_path` directly (same as `repoops scan`/`run`).
  `diff_stat`/`cached_diff_stat` run each stat line's path segment (including
  both sides of a rename's `old => new`) through the same redaction function
  before the line is kept — see "Redaction examples" above; the pattern is
  identical, only the input (a `diff --stat` line instead of a porcelain status
  line) differs.
- **Excludes its own output from the facts it collects.** `.repoops/` entries are
  filtered out of `git status`/`git diff --stat` output before counts, `dirty`,
  `notable_paths`, and diff stats are computed, so writing a checkpoint never
  shows up as drift the next time `repoops checkpoint` or `repoops resume` runs
  (see `docs/DATA_CONTRACTS.md` → "Handoff schema").
- **`repoops resume` never claims safety it cannot verify.** A missing checkpoint,
  invalid JSON, an unsupported `schema_version`, or a repository-root mismatch are
  each reported as an explicit `BLOCKING` drift item — never silently ignored or
  downgraded — and the command exits non-zero.
- **`.repoops/` is not auto-added to `.gitignore`.** Whether to commit or ignore
  checkpoint files is left to the user; see README "Should you commit `.repoops/`?".

## Worklog evidence (`repoops.worklog`)

`repoops worklog-scan` / `worklog-weekly` / `worklog-export` are subject to the same core rule: they are evidence collection and review tooling, not a repository repair tool and not a payroll system.

- **No new Git commands.** `worklog-scan` introduces zero new Git invocations. It calls the same `build_snapshot` function used by `repoops scan`/`repoops run`, so every command it runs is already covered by "Allowed Git commands" above. It never calls `--fetch`, so it never touches the network.
- **Reuses `build_snapshot`.** There is no separate worklog scanning path — `worklog-scan` is a thin wrapper that scans once and persists the result. Any future change to scan safety (allowed commands, redaction, timeouts) automatically applies to worklog scans.
- **Does not read file contents.** Like the rest of `repoops`, only paths, counts, branch/HEAD names, and risk flags are inspected. Diffs and file contents are never read or stored.
- **Redacts paths defensively before SQLite insert.** `git_scan.redact_secret_like_path` already redacts `notable_files` before they reach `Snapshot`, but `record_snapshot` redacts them again immediately before the `INSERT`, so the SQLite store stays safe even if it is ever called with a snapshot from a path that skipped the first redaction. Only the redacted paths (and a SHA-256 hash of them, never a hash of raw contents) are stored — never a raw path.
- **Does not approve hours.** `worklog-weekly` and `worklog-export` only ever produce `WorklogCandidate` rows — a wide `real_hours_estimate_range`, a `suggested_reportable_hours` capped at 4 hours/day, and a `confidence` level. `repoops` never asserts a specific value is correct, and no code path marks a candidate "approved."
- **Does not generate payroll reports.** `worklog-export --format csv` writes raw candidate rows only; there is no invoice, timesheet, or payroll rendering anywhere in `repoops`. Turning candidates into a timesheet is an explicitly human (or human + external-tool) step — see README "Feeding the weekly pack to Claude Tasks."
- **Does not mutate repositories.** `worklog-scan` only reads Git state and writes to its own local SQLite file (`defaults.worklog_db`); it never writes into a scanned repository's working tree, index, or refs.
